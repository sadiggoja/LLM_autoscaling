# Session update — 2026-06-01 / 2026-06-02

## Goal
Introduce a heterogeneous workload alongside the homogeneous localization
service so MARLISE can be benchmarked on two different services side by side,
with deployment names that are explicit about which workload runs where.

## Final state
Two distinct deployments, one per node:

| Deployment | Workload | Service | Ingress path | ConfigMap |
|---|---|---|---|---|
| `localization-api1` (rasp1) | KNN regressor (`spring.pkl`) | `localization-service1` | `/api1/predict` | `localization-code` |
| `predictor-api1` (rasp2) | GradientBoosting (synthetic, 500 trees) | `predictor-service1` | `/api2/predict` | `predictor-code` |

Both deployments still carry the `app=localization-api` and `version=vN`
labels for the existing label-selector / service-selector wiring. Added a
`workload=knn` / `workload=gbr` label for visibility — surface it with
`kubectl get pods -L workload`.

## Code that changed
- **`src/localization/regressor.py`** — restored to the original KNN
  regressor (loads `spring.pkl` + `trained_model.pkl`).
- **`src/predictor/regressor.py`** — new, GradientBoosting CPU-only
  service. Same `POST /predict` shape (`{"feature": int}` →
  `{"x": float, "y": float}`).
- **`configs/elasticity_config.yaml`** — added `service_deployments` list:
  ```yaml
  service_deployments:
    - localization-api1
    - predictor-api1
  ```
- **`src/utils.py`** — new helper `get_deployment_name(agent_id, config=None)`
  that reads the list above; falls back to the legacy `localization-api{id}`
  pattern when the list is unset/short, so single-service setups still work.
- **`src/envs.py`**, **`src/pod_controller.py`**, **`src/infer.py`**,
  **`scripts/eval/benchmark_runner.py`** — every `f'localization-api{i}'`
  on the live benchmark path now goes through `get_deployment_name(i)`.
- **`configs/localization/separate_services.yaml`** — renamed second
  Deployment + Service to `predictor-api1` / `predictor-service1`, pointed
  `/api2/` ingress at `predictor-service1`, split the single ConfigMap mount
  into two (`localization-code` + `predictor-code`), added `workload` label.

## Files NOT touched (intentionally)
- `src/heuristic_agent.py` — agents look up `env.target_deployment` first,
  which now uses the helper. The `deployment_name` default kwarg
  (`"localization-api"`) is only used as a last-resort fallback.
- `src/infer.py:147` (`initialize_agents`, plural) — used by training
  scripts, not the live benchmark; left for a separate pass.
- The KNN container image still ships `joblib`, `pandas`, etc., which the
  GBR pod doesn't need. Both pods use the same image — the predictor pod
  carries a few unused MB.

## Workflow

### One-time (or after renaming things)
```bash
# Create the two ConfigMaps from the two source files
microk8s kubectl create configmap localization-code \
  --from-file=regressor.py=src/localization/regressor.py \
  --dry-run=client -o yaml | microk8s kubectl apply -f -

microk8s kubectl create configmap predictor-code \
  --from-file=regressor.py=src/predictor/regressor.py \
  --dry-run=client -o yaml | microk8s kubectl apply -f -

# Remove the old single-service setup (old ConfigMap + old api2 deployment+service)
microk8s kubectl delete configmap regressor-code --ignore-not-found
microk8s kubectl delete deployment localization-api2 --ignore-not-found
microk8s kubectl delete service localization-service2 --ignore-not-found

# Apply the new manifest
microk8s kubectl apply -f configs/localization/separate_services.yaml
```

### Inspect
```bash
microk8s kubectl get pods -L workload
# localization-api1-...   workload=knn
# predictor-api1-...      workload=gbr
```

### Swap code in either workload (no Docker rebuild)
Edit `src/localization/regressor.py` and/or `src/predictor/regressor.py`, then:
```bash
microk8s kubectl create configmap localization-code \
  --from-file=regressor.py=src/localization/regressor.py \
  --dry-run=client -o yaml | microk8s kubectl apply -f -

microk8s kubectl create configmap predictor-code \
  --from-file=regressor.py=src/predictor/regressor.py \
  --dry-run=client -o yaml | microk8s kubectl apply -f -

microk8s kubectl rollout restart \
    deployment/localization-api1 deployment/predictor-api1
```

### Run benchmark
```bash
python scripts/eval/benchmark_runner.py --config configs/benchmark_config.yaml
```

The benchmark assigns agent_id 1 → `localization-api1` (KNN), agent_id 2 →
`predictor-api1` (GBR), based on `service_deployments` in
`configs/elasticity_config.yaml`. Output filenames are unchanged.

## Reverting to a single homogeneous workload
1. Drop the `service_deployments:` entry (or shorten to one name) in
   `configs/elasticity_config.yaml`. The helper falls back to
   `localization-api{i}`.
2. Re-apply the original `separate_services.yaml` from git history if you
   want the old `localization-api2` back.

# Session update — 2026-06-03 (heterogeneous benchmark run + comparison)

## Goal
Run the full benchmark on the heterogeneous setup (`localization-api1` KNN +
`predictor-api1` GBR), compare against the existing homogeneous baseline in
`results/benchmark/small_3105/`, and surface the key differences in RL-agent
behaviour when one of the two pods is structurally heavier.

## What happened
- 3-iteration smoke run produced `results/benchmark/small/{ppo,ddpg,mdqn,k8s_vpa}_iter{0,1,2}_*`
  with the new pod naming. Sanity-checked that agent_id 0 → KNN, agent_id 1 → GBR.
- Renamed those three iterations to `iter17..19` to make room for the
  17-iteration production run starting at `iter0`. Final state:
  20 iterations × 4 algorithms (no LLMs yet on heterogeneous).
- Aggregate comparison written up directly in chat (no committed deliverable
  beyond the recap in this file).

## Headline findings — HOM vs HET (RL-only so far)

Per-algorithm rollup across all 20 iterations, all phases, both agents:

| Algorithm | Run | Mean RT (ms) | p99 RT (ms) | SLA breach | Reward |
|---|---|---|---|---|---|
| PPO | HOM | 15 | 249 | 1.0% | 1.403 |
| PPO | HET | **244** | **2361** | **23.4%** | 1.089 |
| DDPG | HOM | 11 | 101 | 0.4% | 1.341 |
| DDPG | HET | **250** | **2446** | **23.4%** | 0.696 |
| MDQN | HOM | 43 | 1028 | 3.3% | 1.645 |
| MDQN | HET | **345** | **3241** | **28.4%** | 0.604 |
| k8s_vpa | HOM | 341 | 3428 | 26.0% | 0.472 |
| k8s_vpa | HET | 388 | 2957 | 34.3% | 0.508 |

Per-agent breakdown (high-RPS phase) shows the asymmetry clearly: agent 1
(predictor/GBR) breaches SLA ~90% of steps under PPO/DDPG/MDQN while agent 0
(localization/KNN) stays near its homogeneous baseline. CPU% reported by both
pods is nearly identical (~33% under PPO) despite RT differing by 100×, which
is the key informational failure: **the observation vector (CPU%) is invariant
under per-request-cost shifts, so no policy operating on it can distinguish
the heavy pod from the light one**.

### DDPG inverts the allocation
At high RPS, DDPG gives the light KNN pod 708 m and the heavy GBR pod 322 m
— the opposite of what's needed. PPO is "symmetric blind" (both ~467 m);
MDQN is noisy (435 m vs 377 m, std ±47%); k8s_vpa is the only one that
slightly *increases* allocation on the heavy pod (236 m vs 118 m at iter 0
high) by reacting to CPU%.

### Reward is misleading
k8s_vpa reward *rises* under heterogeneity (0.472 → 0.508) even though its
SLA breach goes from 26% to 34%, because the reward function rewards CPU
headroom which the light pod releases more aggressively in HET. **Reward is
not a faithful proxy for outcome under heterogeneity** — must report SLA
independently.

# Session update — 2026-06-04 (RQ1 deep-dive HTML report)

## Goal
Turn the qualitative "low/medium/high" rankings in the paper's Results
section into a quantitative, mechanism-level analysis with one plot per
finding. The user is structuring the paper around three research questions;
RQ1 = "how does LLM-based autoscaling compare to RL and heuristic on a
homogeneous workload" — backed by the existing `results/benchmark/small_3105/`
data which already contains 20 iter × 7 algorithms (PPO, DDPG, MDQN,
k8s_vpa, Llama 3 8B, Mistral 7B, Qwen 2.5 7B via Ollama).

## What was added
| Path | Purpose |
|---|---|
| `analysis/generate_rq1.py` | Self-contained Python script. Loads 50 400 rows across 7 algorithms × 20 iter, computes all metrics, renders 10 figures + the HTML. Re-runnable from any cwd. Dependencies: pandas, numpy, matplotlib (already in the notebook venv; if missing, `pip install --user pandas matplotlib numpy`). |
| `analysis/figures/rq1_*.png` | 10 figures @ 200 dpi. Filenames: `decision_latency_cdf`, `open_loop_overlay`, `cpu_limit_violin`, `transition_window_bars`, `reward_vs_sla`, `sustained_rt_floor`, `pareto_latency_sla`, `action_mix`, `rt_cdf_per_phase`, `action_volatility`. |
| `analysis/RQ1.html` | Standalone HTML report with light + dark mode CSS, TL;DR table, transition-window table, 10 finding sections (each: headline → key number → figure → architectural explanation → paper-ready sentence), and a closing one-sentence answer. |

## The 10 findings (one section + one figure each in the HTML)

1. **LLM decisions exceed the 1 s control interval 100 % of the time** —
   Llama 3 8B mean 9.7 s (p99 = 15 s), Mistral 7B mean 3.7 s (p99 = 18 s),
   Qwen 2.5 7B mean 1.7 s (p99 = 9.3 s). RL & VPA finish in 0.3–3 ms.
2. **Smooth LLM transitions are partly an open-loop artifact** — the
   controller reuses `last_action` when an inference is still in flight, so
   LLMs emit ~1 new decision per 6–10 control steps. Smoothness reflects
   fewer decisions, not better ones.
3. **Qwen fails through under-actuation, not slow reaction** — 98.9 % no-op
   rate, max cpu_limit = 100 m. Prompt-comprehension / tool-use failure
   specific to smaller LLMs.
4. **RL spike-and-recover beats LLM smooth-but-elevated** — PPO/DDPG/MDQN
   return to ≈ 7 ms sustained RT after every transition; Llama settles at
   46–55 ms, Mistral 210–238 ms, Qwen 2.4–5.7 s.
5. **Reward is a poor proxy for SLA outcome** — MDQN highest reward (1.645)
   but ranks third on SLA (3.3 % breach) behind DDPG (0.4 %) and PPO (1.0 %).
6. **LLM agents share a sustained-latency floor** — even Llama 3 8B is ≈ 8×
   higher than RL; Mistral ≈ 30× higher. Three causes stack: discrete 50 m
   action grid, stochastic sampling, open-loop windows.
7. **No LLM is on the Pareto front** — PPO and DDPG strictly dominate Llama
   on both decision-latency and SLA simultaneously. Pareto front is
   VPA → MDQN → PPO → DDPG.
8. **Action mix differs systematically** — PPO/Llama hold the CPU limit
   ≈ 97 % of steps; DDPG churns (81 % no-op); Qwen 99 % no-op at the floor;
   VPA scales aggressively in both directions on edge triggers.
9. **Per-phase RT CDFs reveal distinct failure modes** — RL = thin
   distributions with rare long tails; Mistral = fat body 100–500 ms in
   medium/high; Qwen = bimodal in high (queue-empty vs queue-full regimes).
10. **Action volatility (σ/μ of cpu_limit)** — RL clusters at 0.37–0.46
    (controlled adaptation); Llama 0.58 (decisive but coarse); Mistral 0.69
    (volatile); Qwen 0.33 at the wrong absolute level (76 m).

## Closing one-sentence answer (in the HTML)
> "Under homogeneous in-place autoscaling, RL-based agents dominate every
> quantitative axis and form the Pareto front together with the heuristic
> VPA baseline; all three LLM-based agents are strictly dominated, with the
> best LLM (Llama 3 8B at 96.8 % SLA satisfaction, 9.7 s mean decision
> latency) trailing PPO and DDPG on both axes simultaneously. The smaller
> LLM agents fail in distinct ways — Qwen 2.5 7B from chronic
> under-actuation, Mistral 7B from prompt-driven oscillation. LLM-based
> autoscaling on a homogeneous workload therefore offers no quantitative
> advantage; its remaining argument is qualitative (decision inspectability,
> zero training-data requirement) and must be weighed against an ≈ 10⁴×
> decision-latency penalty and a measurable sustained-RT floor."
